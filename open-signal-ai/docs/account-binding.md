# Account Binding (Telegram ID ↔ Trader ID)

Код: `apps/api/src/binding/`. Тесты: `apps/api/test/binding.test.ts` (18 сценариев).

## Состояния
`telegram_created → waiting_for_trader_id → registration_pending → registration_verified → account_bound`, плюс `binding_conflict` и `manual_review`. Разрешённые переходы описаны в `state-machine.ts`; запрещённый переход — это ошибка программы, а не тихое действие.

## Правила
1. Вход только через Telegram (проверенная initData), без email и пароля.
2. `click_id` — 128 случайных бит, не вычисляется из Telegram ID; живёт 90 дней.
3. Событие, пришедшее по чужому `click_id`, никогда не привязывает этого пользователя.
4. Если один Trader ID заявили несколько аккаунтов без `click_id`, его не получает никто, все уходят в `manual_review`.
5. Пользователь не может сам сменить привязанный Trader ID. Сделать это может только администратор, с причиной и записью в `audit_logs`. В журнал Trader ID попадает в замаскированном виде.
6. События сохраняются, даже если пользователь ещё не ввёл Trader ID, и используются позже.
7. Повторная доставка события получает 200 и увеличивает `deliveryCount`, но повторно не обрабатывается.
8. Финансовые события (FTD, депозит) — только аналитика. Они не меняют состояние и доступ. Академия, демо-симулятор и профиль открыты всегда (`binding/access.ts`).

## Настройка партнёрской программы (без изменения кода)
Документ в `partner_sources`:
- `auth`: `hmac_sha256` (заголовок с подписью сырого тела или query) или `shared_secret` (заголовок или параметр); секрет хранится в зашифрованном виде;
- `ipAllowlist`: необязательный список IP;
- `mapping`: какие параметры партнёра означают event_id / тип события / trader_id / click_id / время;
- `eventTypeMap`: названия событий партнёра → `registration | ftd | deposit | other`.

Адрес для партнёра: `https://<API>/postback/<sourceId>` (GET или POST).

> Какой способ аутентификации доступен, зависит от партнёрской программы. Подключение реальной программы — отдельный шаг после получения её документации.
