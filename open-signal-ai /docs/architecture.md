# Архитектура OPEN SIGNAL AI

## Один сервер — много ботов

```
Telegram (бот 1 … бот N)
   │  POST /tg/webhook/:botId   + заголовок secret_token
   ▼
API (один процесс Node.js)
   ├─ HTTP pipeline: security headers → CORS → body limit → routing → rate limit → handler → errors → access log
   ├─ Tenant: TenantScope(botId) — все документы и запросы привязаны к botId
   ├─ BotRepository: конфиги ботов в памяти (кэш 30 с), токены зашифрованы
   ├─ Auth: Telegram initData (HMAC) → сессия, привязанная к botId
   ├─ Account Binding + postback
   ├─ Logs: error_logs (склейка одинаковых ошибок), audit_logs, bot_stats_daily (пакетная запись)
   ├─ Admin: сессии (cookie HttpOnly, в базе только sha256), scrypt-пароли, блокировка подбора, права менеджеров по ботам
   ├─ Telegram provisioning: getMe → setWebhook(secret) → тексты RU/UK/EN → кнопка Mini App → аватар
   ├─ Static: /admin/ и /app/ из dist/web (CSP, HSTS, immutable-кэш ассетов)
   └─ Storage: DocumentStore → Firestore REST (production) / локальный JSON (разработка и тесты)
Mini App / Админка  ──►  только API (прямого доступа к базе нет)
```

### Запуск в production
- Один процесс `node apps/api/src/server.ts` (Node 22.18+ исполняет TypeScript напрямую, без отдельной компиляции сервера). Слушает `0.0.0.0:$PORT`.
- При старте: проверка переменных (в ошибке — только имена), проверка доступа к Firestore (при ошибке сервер не стартует, Render оставляет прежнюю версию), затем в фоне: создание индексов и TTL через Firestore Admin API и перенастройка webhook, если изменился публичный адрес.
- `SIGTERM` → корректное завершение: сброс счётчиков статистики, закрытие соединений.
- Сборка фронтенда: `scripts/build-web.mjs` (esbuild + компилятор Tailwind v4), файлы с хешами в именах.

### HTTP без фреймворка
Вся логика (маршруты, CORS, лимиты, ошибки) находится в `apps/api/src/http/pipeline.ts`, транспорт — `node:http`. Тесты прогоняют тот же конвейер, что и production; тело запроса приходит «как есть» (это нужно для проверки HMAC-подписи postback). Меньше зависимостей — меньше уязвимостей в аудите.

### Firestore
Адаптер `storage/firestore/` работает через REST API v1 с JWT сервисного аккаунта (RS256 через `node:crypto`), без `firebase-admin`. Транзакции: `beginTransaction → commit`, повтор при `ABORTED`; повторяются только безопасные запросы. Весь набор тестов прогоняется и через этот адаптер (`npm run test:firestore`, тестовый двойник REST API).

### Изоляция данных
- ID документов пользователя: `{botId}_{telegramId}`. Один и тот же человек в двух ботах — это два независимых профиля.
- `botId` берётся только из URL плюс проверенной сессии или секрета webhook, никогда из тела запроса.
- Сессия подписана и содержит `botId`; токен бота A отклоняется маршрутами бота B (покрыто тестом).
- initData, подписанная токеном бота A, не проходит проверку у бота B (покрыто тестом).

### Масштаб 50–100 ботов
- Тест `100 bots on one server` создаёт 100 ботов и проверяет независимость конфигов и сессий.
- Конфиги кэшируются в памяти; синтетические цены не хранятся, а вычисляются детерминированно (одинаково на любом числе серверов).
- Счётчики активности копятся в памяти и пишутся пакетами, а одинаковые ошибки склеиваются: квота записей Firestore расходуется экономно.
- Лимитер запросов хранится в памяти процесса. При переходе на несколько экземпляров сервера его нужно вынести в общее хранилище.

## Безопасность
| Угроза | Защита |
|---|---|
| Утечка токенов ботов | AES-256-GCM, отдельный IV, AAD `bot:<id>:token`, поддержка ротации ключа, маскирование в UI и логах |
| Подделка пользователя | Проверка подписи initData, свежести `auth_date`, сравнение за постоянное время |
| Подделка webhook | `secret_token` (хранится только хэш), сравнение за постоянное время |
| Повтор webhook | `create(webhook_updates/{botId}_{update_id})`: повтор получает 200, но не обрабатывается |
| Подделка postback | HMAC-подпись или общий секрет, список разрешённых IP, проверка формата |
| Повтор postback | ID события = хэш ключа события, `create` в транзакции |
| Перегрузка | Token bucket по боту/источнику и IP (вход в админку — 10 попыток), лимит тела 64 КБ (загрузка медиа — 800 КБ) |
| Подбор пароля админки | scrypt, блокировка на 15 минут после 8 ошибок, сессии HttpOnly + SameSite=Strict + Secure, CSRF-заголовок |
| Встраивание админки | CSP `frame-ancestors 'none'`, `X-Frame-Options: DENY`; Mini App разрешено встраивать только Telegram |
| Утечка в логах | Автоматическое скрытие полей token / secret / initData / authorization / hash, в лог пишется только путь без query |
| Доступ к базе из браузера | `firestore.rules` запрещает весь клиентский доступ |

## Данные рынка: Forex и OTC
Каждый режим (`forex`, `otc`) получает данные через интерфейс `MarketDataSource` (`apps/api/src/market/source.ts`). Сейчас для обоих зарегистрирован `SimulationSource`: синтетический ряд, свой для каждого бота, режима и инструмента. Forex-симуляция стоит на выходных, как настоящий рынок; OTC работает круглосуточно. Статус данных — `SIMULATED`, и Mini App всегда показывает отметку DEMO / SIMULATED.

Чтобы подключить реальный источник, достаточно реализовать `MarketDataSource` и зарегистрировать его для режима: экраны, демо-сигналы, история и статистика не меняются. Пока источник синтетический, демо-сигналы открыты всем; для реального источника действуют правила доступа модуля «Сигналы».

## Онбординг и postback
Статус онбординга (`registration → registration_started → trader_id → pending_review → completed`) вычисляется на сервере из записи пользователя при каждом запуске Mini App, поэтому не зависит от устройства. Подтверждение регистрации и депозиты приходят только из postback-событий (`registration`, `ftd`, `redeposit`) с идемпотентностью по ID события; без источника статус депозита — «нет данных», никаких фиктивных подтверждений.
