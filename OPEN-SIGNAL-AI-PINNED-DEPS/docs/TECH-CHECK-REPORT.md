## Что исправлено

### 1. Потеря повторных депозитов (серьёзно)
**Было:** повторный депозит без ID события (а Pocket Partners такой ID не передаёт) склеивался с предыдущим, если сумма и Trader ID совпадали в течение 10 минут. Пользователь, пополнивший счёт дважды на $100, получал в учёте один депозит.

**Стало:**
- Каждый повторный депозит засчитывается.
- Если за 10 минут пришёл депозит с тем же Trader ID и суммой, он помечается «Возможный повтор». В «Ошибках интеграции» появляется `POSSIBLE_DUPLICATE`.
- Администратор может нажать «Исключить» с указанием причины, если убедился, что это повторная доставка. Событие не удаляется, итоги пересчитываются, действие пишется в журнал (`finance.event_excluded`). «Вернуть в учёт» отменяет решение.
- Исключать могут только владелец и менеджер с правом управления привязками этого бота.

Почему не автоматически: без ID события повторную доставку нельзя отличить от второго настоящего депозита. Потерять настоящий депозит хуже, чем показать администратору возможный повтор. На доступ к приложению повторные депозиты не влияют.

### 2. FTD
- FTD — только один на Trader ID, даже если партнёр пришлёт разные ID событий. Раньше при настроенном поле «ID события» два FTD с разными ID засчитывались дважды.
- Сумма FTD берётся **только** из события `ftd`. Раньше, если повторный депозит приходил раньше FTD, его сумма могла стать «первым депозитом» и открыть приложение.
- Есть повторные депозиты, но нет события FTD → шаг 3 «Проверяется», приложение не открывается.

### 3. click_id
- Новые коды — 32 символа `0-9a-f` (те же 128 случайных бит). Прежний формат содержал заглавные буквы, `-` и `_`. Трекеры, которые меняют регистр или вырезают такие символы в Sub ID, ломали бы сопоставление.
- Код, вернувшийся заглавными буквами, находится.
- Коды прежнего формата, уже выданные пользователям, продолжают работать.
- «Проверить ссылку» в админке теперь проходит до 8 редиректов. Перед каждым шагом заново проверяется, что адрес не ведёт во внутреннюю сеть. На каждом шаге видно, есть ли тестовый click_id в адресе. Значения остальных параметров скрыты.

### 4. Зависимости
- Точные версии прямых зависимостей во всех 7 `package.json`. Помимо ранее закреплённых `react` 19.2.8, `react-dom` 19.2.8, `zod` 3.25.76, `esbuild` 0.28.2, `tailwindcss` 4.3.3 и `typescript` 6.0.3, диапазоны типов заменены на точные версии: `@types/node` 22.15.0, `@types/react` 19.2.0, `@types/react-dom` 19.2.0. Peer dependency `react` в `packages/ui` закреплена на 19.2.8.
- Проверка всех секций `dependencies`, `devDependencies`, `optionalDependencies` и `peerDependencies` во всех манифестах: диапазонов (`^`, `~`), `*`, тегов и git/url-спецификаций не осталось.
- Важно: новые версии `@types/*` закреплены точными номерами, но из-за отсутствия доступа к npm в этой среде их установку и совместимость отдельно не перепроверял. Сборка из отчёта выше была выполнена до этой правки.
- `.npmrc`: `package-lock=true`, `save-exact=true`.
- Новая команда `npm run lock:check` (входит в `npm run check`). Она проверяет:
  - что `package-lock.json` есть;
  - что он совпадает со всеми `package.json`;
  - что установленные пакеты совпадают с lock-файлом.
- Проверена на 5 случаях: нет файла, совпадает, установлена другая версия, совпадает после исправления, `package.json` изменён без обновления lock.

**Почему в архиве нет `package-lock.json`.** Настоящий lock-файл содержит контрольные суммы каждого пакета для всех систем (macOS, Linux, Windows). В среде проверки нет доступа к npm. В локальном кэше нет данных `@types/node`, `@types/react`, `@types/react-dom` и сборок esbuild для macOS. Собрать файл вручную значило бы вписать непроверенные данные. Вместо этого `npm install` у вас создаст правильный файл; его нужно добавить в git (шаги — в `docs/update-render.md`). Render выполняет `npm install`, а эта команда устанавливает ровно версии из lock-файла.

## Pocket Partners: что подтверждено источниками

Официальной публичной документации Pocket Partners не найдено. Есть два независимых открытых описания настройки postback: инструкция MVP Project для Pocket Partners и обзор программы на affdays.com. Оба совпадают:
- поля postback: `click_id`, `trader_id`, `sumdep`; флаги событий `reg`, `ftd`, `dep`;
- для регистрации, депозита и повторного депозита настраиваются отдельные postback;
- названия параметров в URL можно переименовать (например, `clickid={click_id}`, `playerid={trader_id}`, `sum={sumdep}`).

Ни один источник не упоминает ID события, время депозита или валюту. Код не использует придуманных макросов: шаблоны в админке содержат только `{click_id}`, `{trader_id}`, `{sumdep}`. Поля «ID события» и «Время» в настройках источника оставлены пустыми и необязательными.

## Какие тесты добавлены
- Два настоящих депозита одной суммы с интервалом в минуту → оба засчитаны, второй помечен.
- Исключение и возврат события администратором: нужна причина, у менеджера без прав — отказ, пишется журнал, итоги пересчитываются, событие сохраняется. Регистрацию исключить нельзя.
- Ключи событий: FTD один при разных ID событий; повторные депозиты с ID или временем различаются; без них каждая доставка — отдельное событие.
- Порядок депозитов: повторный депозит не становится FTD; без события FTD — «Проверяется».
- Депозиты, пришедшие **до** ввода Trader ID, засчитываются после привязки.
- 3 бота, один человек в каждом: регистрации, FTD и повторные депозиты попадают только в свой бот. Чужой click_id не засчитывает депозит.
- click_id заглавными буквами, click_id старого формата, просроченный и неизвестный click_id (ответ 400 и запись в «Ошибки интеграции»).
- Существующие пользователи после обновления: бывший гость → шаг 1; старые промежуточные состояния → шаг 2; привязан без депозита → шаг 3; привязан и есть FTD от старого источника бота → открыт; уже завершил → остаётся открыт; на ручной проверке → экран поддержки; новый → шаг 1.
- Проверка ссылки: цепочка из 4 шагов, где click_id пропадает на последнем; редирект во внутреннюю сеть не запрашивается; петля редиректов обрывается на 8 шагах; секреты в адресах скрыты.

## Что ещё нужно проверить на реальном Pocket Partners

1. **Параметр трекинговой ссылки для click_id.** Его название есть только в кабинете Pocket Partners. Без него регистрацию нельзя подтвердить.
2. **Доходит ли click_id через редиректы.** Нажмите «Проверить ссылку» в админке на Render — сервер пройдёт реальную цепочку. Окончательно это подтверждает тестовая регистрация: в «Истории» должно появиться событие «Регистрация» со статусом «Ждёт ввода Trader ID» или «Привязано».
3. **Можно ли дописать в URL postback свои параметры** `key=…` и `event=reg|ftd|dep` (поле Data format). Если нет, сервер ответит 401, и это будет видно в «Ошибках интеграции».
4. **Формат `{sumdep}`.** Принимаются числа вида `50`, `50.5`, `50,5`. Если партнёр присылает сумму с разделителем тысяч (`1,000.50`) или символом валюты, сумма не распознаётся. Депозит тогда получит «Проверяется», а не неверную сумму. Посмотрите первые реальные события в «Истории».
5. **Валюта.** Сумма считается в долларах, потому что валюта не передаётся. Если в вашем кабинете суммы не в USD — сообщите, порог $10 придётся пересчитать.
6. **Повторяет ли Pocket Partners отправку** при ошибках. Если повторы частые, в «Истории» будет много пометок «Возможный повтор». Тогда стоит спросить менеджера Pocket Partners о макросе ID транзакции: если он есть, впишите его в поле «ID события» источника, и повторы будут распознаваться автоматически.
7. **Чистая установка из интернета** (`npm install`) и проверка типов с официальными пакетами `@types/react` — выполняются у вас командой `npm run check`.
8. **Ровно Node 22.18.0** не запускался. Проверено на 22.23.4; минимальную версию проверяет `scripts/check-node.mjs`.
